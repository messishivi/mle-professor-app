## 1. Which paper/product is this?

**Paper:** *LoRA: Low-Rank Adaptation of Large Language Models* — Hu, Shen, Wallis,
Allen-Zhu, Li, Wang, Wang, Chen (Microsoft), arXiv:2106.09685 (Oct 2021).

**Not to confuse with:** the Hugging Face `peft` library's `LoraConfig` — that is the
*product/implementation* of this paper, and it's what you'll actually import. Also not
adapters (Houlsby) or prefix-tuning: LoRA's distinguishing claim is **zero additional
inference latency**, because the learned update is merged back into the frozen weights
after training.

**One-line idea:** freeze the pretrained weights W₀, learn a low-rank delta
ΔW = BA (B: d×r, A: r×k, r ≪ min(d,k)), train only A and B. Forward becomes
h = W₀x + (α/r)·BAx; at serve time, fold BA into W₀.

## 2. Relevance map vs your system (nanoGPT, GPT-2 124M, single GPU)

Rows are renamed to *your* modules, not generic production vocabulary.

| nanoGPT module | Verdict | Why |
|---|---|---|
| `model.py` → `CausalSelfAttention.c_attn` (fused QKV, 768→2304) | **Use** | The primary LoRA target. The paper's sweet spot was W_q/W_v; on nanoGPT's fused `c_attn` the practical equivalent is the whole projection (includes W_k — slightly more params, far simpler code). |
| `model.py` → `CausalSelfAttention.c_proj` (768→768) | **Use** | Secondary target; cheap (12K params/block at r=8) and consistently helps in reproductions. |
| `model.py` → `MLP.c_fc` / `MLP.c_proj` | **Ignore** (for now) | Paper ablations: attention-only adaptation matches full fine-tuning; adding MLP ~2.7× the adapter params for marginal gain. Revisit only if attention-only underperforms your eval gate. |
| `model.py` → embeddings (`wte`, `wpe`), `lm_head` | **Ignore** | Not LoRA targets in the paper; unfreezing them reintroduces the memory cost you're trying to avoid. |
| `train.py` → optimizer + training loop | **Adapt** | Freeze the base model; build the optimizer **only** over parameters with `lora_` in the name. Everything else in the loop (lr schedule, grad clipping, checkpoint cadence) stays. |
| `train.py` → checkpointing | **Adapt** | Save *only* the adapter state dict (~1.7 MB fp32 at r=8) instead of the full 500 MB checkpoint. This is the operational win: one base checkpoint + N tiny task adapters. |
| `data/*/prepare.py` (tokenized `.bin`) | **Ignore** | LoRA is data-agnostic. No change to the data contract — same binaries, same batches. |
| `sample.py` (generation) | **Use** | Call `merge_lora()` once at load: W ← W₀ + (α/r)BA. After the merge, `sample.py` is byte-identical — zero latency change, which is the paper's headline claim over adapters. |
| `hellaswag.py` / val-loss eval | **Adapt** | Same harness, new comparison: LoRA run vs your existing full-FT baseline on identical tokens. |

**Parameter math (GPT-2 124M: n_layer=12, n_embd=768, r=8, α=16):**
per block: `c_attn` 8·(768+2304) = 24,576 + `c_proj` 8·(768+768) = 12,288 → 36,864.
×12 blocks = **442,368 trainable ≈ 0.36% of 124M.** Optimizer state (AdamW) shrinks
proportionally — this is what makes single-GPU fine-tuning comfortable.

## 4. Implementation path (this quarter)

**Step 1 — Add `lora.py` (one new file, ~60 lines, no dependency on `peft`).**
Wrap target `nn.Linear`s in place; freeze everything else:

```python
# lora.py — minimal LoRA for nanoGPT (checked against model.py)
import math
import torch
import torch.nn as nn

class LoRALinear(nn.Module):
    def __init__(self, linear: nn.Linear, r=8, alpha=16, dropout=0.05):
        super().__init__()
        self.linear = linear
        self.linear.weight.requires_grad = False
        if self.linear.bias is not None:
            self.linear.bias.requires_grad = False
        d_in, d_out = linear.in_features, linear.out_features
        self.scaling = alpha / r
        self.lora_A = nn.Parameter(torch.empty(r, d_in))   # (r, d_in)
        self.lora_B = nn.Parameter(torch.zeros(d_out, r))  # (d_out, r)
        nn.init.kaiming_uniform_(self.lora_A, a=math.sqrt(5))  # B=0 => ΔW=0 at init
        self.dropout = nn.Dropout(dropout) if dropout > 0 else nn.Identity()

    def forward(self, x):
        return self.linear(x) + self.dropout(x) @ self.lora_A.T @ self.lora_B.T * self.scaling

    def merge(self):
        # fold adapters into frozen weights: zero inference overhead
        with torch.no_grad():
            self.linear.weight.add_((self.lora_B @ self.lora_A) * self.scaling)

def apply_lora(model, target_suffixes=("c_attn", "c_proj"), r=8, alpha=16, dropout=0.05):
    for name, module in list(model.named_modules()):
        # nanoGPT names look like transformer.h.0.attn.c_attn
        if isinstance(module, nn.Linear) and name.split(".")[-1] in target_suffixes:
            parent = model.get_submodule(".".join(name.split(".")[:-1]))
            setattr(parent, name.split(".")[-1], LoRALinear(module, r, alpha, dropout))
    for name, p in model.named_parameters():
        p.requires_grad = ("lora_A" in name) or ("lora_B" in name)
    n_train = sum(p.numel() for p in model.parameters() if p.requires_grad)
    n_total = sum(p.numel() for p in model.parameters())
    print(f"LoRA: {n_train/1e6:.3f}M trainable / {n_total/1e6:.1f}M total ({100*n_train/n_total:.2f}%)")
    return model
```

**Step 2 — Wire into `train.py` (data contract: unchanged).**
After model construction / `from_pretrained`, before the optimizer:
```python
from lora import apply_lora
apply_lora(model, r=8, alpha=16)  # prints: LoRA: 0.442M trainable / 124.4M total (0.36%)
optimizer = torch.optim.AdamW(
    [p for p in model.parameters() if p.requires_grad], lr=1e-4, betas=(0.9, 0.95))
```
Same `prepare.py` binaries, same batching. Save adapters only:
```python
torch.save({k: v.cpu() for k, v in model.state_dict().items() if "lora_" in k},
           "lora_adapters.pt")  # ~1.7 MB
```
Eval: the existing val-loss loop, unchanged.

**Step 3 — Eval gate (kill criteria defined up front).**
Run LoRA (r=8) vs your current full-FT baseline on the *same* token budget.
Ship gate: val loss within **0.02** of the full-FT run *and* no regression on your
downstream check (`hellaswag.py` ≥ −1 pt). The paper reports LoRA ≥ full FT on GPT-2;
if you miss the gate, one retry at r=16 — then kill. (At 124M, full FT is cheap
enough that LoRA has to earn its place on checkpoint size and multi-task reuse,
not just VRAM.)

**Step 4 — A/B the adapter, not the model.**
Keep one frozen base checkpoint. Fine-tune one adapter per domain/task. A/B =
swap the 1.7 MB file, not a 500 MB checkpoint. Track: which adapter, which base
commit, val loss at swap time.

**Step 5 — Serve with the merge.**
At load time in `sample.py` (or your server), load base → load adapter state dict
into the `LoRALinear` modules → `merge()` each → the model is now a plain GPT
again. No `peft`, no latency delta, no serving code fork.

## 5. Skip list

- **Adapter/prefix-tuning variants that insert layers** — they add inference latency;
  LoRA's merge is the reason to pick it here.
- **LoRA on `MLP.c_fc`/`c_proj`, embeddings, or `lm_head`** — more params, no
  evidence of gain at this scale; keep the 0.36% footprint.
- **QLoRA / 4-bit base weights** — solves a problem you don't have: 124M fits in
  VRAM many times over. Adds bitsandbytes complexity for zero benefit here.
- **Multi-adapter serving stacks** — you have one task; don't build the
  infrastructure for N adapters before the first one clears the eval gate.
- **Rewriting `train.py`'s loop** — DDP, grad accumulation, and checkpoint cadence
  are orthogonal; touch only the optimizer's parameter list.
